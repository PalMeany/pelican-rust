# 0012. Выполнение расписаний: синхронная и фоновая очередь

**Статус:** Accepted

**Контекст.** В оригинале `p:schedule:process` (cron, каждую минуту) ставит `RunTaskJob` в очередь
Laravel с задержкой `time_offset`; ручной запуск (`/execute`) выполняет первую задачу через
`dispatchNow`, следующие — снова через очередь. При `QUEUE_CONNECTION=sync` `SyncQueue` игнорирует
задержки, выполняет джоб сразу, вызывает его `failed()` и пробрасывает исключение вызывающему —
поэтому ошибка любой задачи цепочки становится ответом HTTP-запроса. Difftest-окружение оригинала
работает именно в `sync`.

**Решение.** `pelican_api::jobs` повторяет `ProcessScheduleService`/`RunTaskJob`: `QUEUE_CONNECTION=sync`
выполняет следующую задачу inline с семантикой `SyncQueue` (перечитывание задачи из БД как
`SerializesModels`, `failed()` и проброс ошибки); любое другое значение — `tokio::spawn` с задержкой,
при ошибке `failed()` + лог (ADR-0009: без таблиц `jobs`/`failed_jobs`). Минутный тикер
`spawn_scheduler` запускается внутри `pelican serve` (выключается `PELICAN_SCHEDULER=false`);
`pelican schedule:process` — разовый запуск.

**Последствия.** Отложенные задачи живут в памяти процесса: при рестарте во время цепочки задача
остаётся `is_queued`, расписание — `is_processing` (как у оригинала при падении воркера; сбрасывается
переключением `is_active`). При нескольких экземплярах панели тикер должен работать только на одном.
