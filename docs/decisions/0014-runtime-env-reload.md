# 0014. Изменение настроек на лету: запись `.env` и перечитывание конфигурации

**Статус:** Accepted

**Контекст.** Страница настроек админки (и инсталлятор) оригинала пишет значения в `.env`
(`EnvironmentWriterTrait` → `Env::writeVariables(..., overwrite: true)` + `config:clear`), и они действуют
со следующего запроса: PHP читает `.env` заново на каждый запрос. У нас конфигурация (`Config`) читается
один раз при старте и доступна как `st.config.*` в ~100 местах.

**Решение.**
- `pelican_core::env::write_variables` — порт `Env::writeVariables` байт в байт (вставка после последней
  строки с тем же префиксом `XXX_`, кавычки `prepareQuotedValue`, пустое значение → `KEY=`); проверено
  выводом PHP в контейнере оригинала.
- После записи страница вызывает `st.request_reload()`. Бинарь держит `Live` (текущий `AppState`
  под `RwLock`); фоновая задача на сигнал перечитывает `.env` (`Env::load` + `Config::from_env`) и
  подменяет состояние через `AppState::rebuild`: пул БД, счётчики троттлинга и канал перезагрузки
  сохраняются, остальное (Wings-клиент, конфиг, шифратор) строится заново. Роутеры API/web
  пересобираются при первом запросе с новым состоянием; уже начатые запросы дорабатывают со старым.
- Планировщик берёт актуальное состояние из `Live` на каждом тике.
- Ошибка разбора нового `.env` не роняет панель: остаётся прежняя конфигурация, ошибка — в лог.

**Последствия.** Код обработчиков не меняется (`st.config.*` остаётся снимком на время запроса).
Переменные окружения процесса по-прежнему важнее `.env` (как у Laravel/Dotenv), поэтому в Docker-установках
настройки, заданные через `environment:`, со страницы не переопределяются — так же, как в оригинале.
Параметры подключения к БД при перечитывании не применяются (пул сохраняется) — их меняют рестартом.
